# タクシー需要予測・集客サポートアプリ 技術設計書

**バージョン:** 0.1(ドラフト)
**作成日:** 2026-07-02
**想定ユーザー:** タクシー運転手(個人・法人問わず)

---

## 1. プロダクト概要

### 1.1 コンセプト

「今、どこに行けば乗客を拾えるか」をリアルタイムで提示するナビゲーションツール。運転手の経験と勘に頼っていた「流し営業」を、データで補強する。

### 1.2 コアバリュー

需要が発生する瞬間は予測可能なイベントに紐づいていることが多い。

| 需要トリガー | 例 | 予測可能性 |
|---|---|---|
| 交通機関の障害 | 山手線が人身事故で運転見合わせ | リアルタイム検知 |
| イベント終了 | 東京ドームのライブが21時終演 | 事前予測(数日前から) |
| 悪天候 | 18時からゲリラ豪雨 | 事前予測(数時間前から) |
| 終電 | 平日0:30以降の繁華街 | 完全に予測可能 |

この4つのトリガーを統合し、地図上に「需要ヒートマップ」と「アクション提案」を表示する。

### 1.3 MVP でやらないこと

- 配車マッチング(乗客側アプリ)— GO・Uber との競合を避け、運転手支援に特化
- X(Twitter)のリアルタイム監視 — API コストが高く、鉄道会社の公式運行情報で代替可能
- 全国展開 — まず1都市(例:東京23区)に絞る

```
└──────────────────┬───────────────────────────┘
                   │

│           需要予測エンジン(Scoring)              │

└──────────────────┬───────────────────────────┘
                   │

│           API サーバー(REST / WebSocket)        │
└──────────────────┬───────────────────────────┘
                   │
┌──────────────────▼───────────────────────────┐
│           モバイルアプリ(運転手向け)             │
│   ・需要ヒートマップ地図                          │
│   ・アラート通知(「○○駅で運転見合わせ発生」)      │

└───────────────────────────────────────────────┘
```

### 2.2 技術スタック(推奨)

| レイヤー | 技術 | 選定理由 |
|---|---|---|
| モバイルアプリ | React Native または Flutter | iOS/Android 同時開発。車載タブレット対応も視野 |
| 地図 | Mapbox GL / Google Maps SDK | ヒートマップ描画性能。Mapbox は従量課金が安い |
| バックエンド | Node.js (NestJS) または Python (FastAPI) | 予測ロジックを Python にするなら FastAPI 統一が楽 |
| DB | PostgreSQL + PostGIS | 位置情報クエリ(「現在地から3km圏内の需要スポット」)が必須 |
| キャッシュ | Redis | 運行情報・気象の最新状態を高速配信 |
| インフラ | GCP(Cloud Run + Cloud Scheduler)| 小規模ならサーバーレスで月数千円から |
| 通知 | Firebase Cloud Messaging | 無料。運転中のアラートの生命線 |

## 3. データソース詳細設計

### 3.1 鉄道運行情報(事故・遅延検知)

**X 監視の代わりにこちらを採用。** 公式情報のため誤検知がなく、無料〜低コスト。

| ソース | 内容 | コスト |
|---|---|---|
| 公共交通オープンデータセンター(ODPT) | JR東・メトロ・都営等の運行情報 API | 無料(開発者登録制) |
| 各鉄道会社の運行情報ページ | ODPT 未対応路線の補完 | スクレイピング(利用規約要確認) |

**処理フロー:**
1. 2〜5分間隔でポーリング
2. ステータスが「平常」→「運転見合わせ」に変化したら即トリガー
3. 該当路線の駅座標から影響エリアを算出し、周辺の需要スコアを加算
4. 対象エリア付近にいる運転手へプッシュ通知:「京浜東北線 運転見合わせ。大井町駅周辺で需要増の見込み」

**補足:** X 監視は Phase 2 以降のオプション。公式発表より数分早い検知が売りになるが、Basic プランでも月額約 $200、誤検知フィルタリングの開発コストも大きい。

### 3.2 気象情報

| ソース | 内容 | コスト |
|---|---|---|
| 気象庁 API(非公式含む) | 天気予報・注意報・ナウキャスト | 無料 |
| OpenWeatherMap / WeatherAPI | 時間別予報、降水確率 | 無料枠あり、有料でも月数十ドル |
| Yahoo!天気 雨雲レーダー API | ゲリラ豪雨の直前検知 | 要確認 |

**ロジック例:**
- 「1時間後に降水確率 70% 以上」→ 帰宅ラッシュ時間帯ならオフィス街の需要スコア加算
- 降り始めの瞬間が最も需要が跳ねるため、ナウキャスト(5分刻み予報)との連携が効果的

### 3.3 イベント情報

最も価値が高いが、統一 API が存在しないため一番手間がかかる部分。

**取得戦略(ハイブリッド):**
1. **主要会場マスタを作る** — 東京ドーム、国立競技場、日本武道館、横浜アリーナ等、需要インパクトの大きい会場 30〜50 箇所を DB 化(収容人数・座標・最寄り駅・タクシー乗り場位置)
2. **イベント情報の収集** — チケット販売サイトの公開情報、会場公式サイト、スポーツは公式日程 API(J.LEAGUE・NPB 等)
3. **終演時刻の推定** — 開演時刻 + 公演種別ごとの平均所要時間(ライブ約3時間、野球約3.5時間など)。実績データが溜まれば精度向上
4. **手動登録・ユーザー投稿** — 運転手自身が「今日ここでイベントある」と登録できる機能。コミュニティデータ化

**アウトプット例:**
> 「東京ドーム(収容5.5万人)21:00 終演予定。20:40 までに水道橋・後楽園エリアへ。混雑回避なら春日通り側で待機推奨」

### 3.4 終電情報

| ソース | 内容 | コスト |
|---|---|---|
| 駅すぱあと WebサービスAPI | 終電時刻・経路検索 | 有料(スタートアップ向けプランあり) |
| ODPT 時刻表データ | 主要路線の時刻表 | 無料 |
| 静的データ自前整備 | 主要駅の終電時刻は年数回しか変わらない | 初期整備の工数のみ |

**MVP では静的データで十分。** 主要ターミナル駅(新宿・渋谷・池袋・東京・品川等)の方面別終電時刻を DB に持ち、「渋谷:田園都市線 終電 0:32 → 0:15 以降ハチ公口側の需要上昇」のようなルールで運用。ダイヤ改正時(年1〜2回)に手動更新。

## 4. 需要予測エンジン設計

### 4.1 スコアリングモデル(MVP はルールベース)

対象都市を 500m メッシュに分割し、各メッシュの需要スコアを 5 分ごとに再計算。

```
需要スコア = 基礎需要(曜日×時間帯の統計値)
           + 運行障害ボーナス(影響駅からの距離減衰 × 路線利用者数)
           + イベントボーナス(収容人数 × 終演までの時間関数)
           + 天候ボーナス(降水強度 × エリア特性)
           + 終電ボーナス(終電後経過時間 × 繁華街係数)
```

各係数は初期値を仮置きし、運用データで調整。

### 4.2 将来の機械学習化(Phase 3)

運転手の実車データ(どこで乗せたか)が溜まれば、教師データとして勾配ブースティング(LightGBM 等)で置き換え可能。ただし MVP 段階では**ルールベースの方が説明可能性が高く、運転手の信頼を得やすい**。「なぜここが赤いのか」を「山手線が止まったから」と説明できることが重要。

### 4.3 通知設計(運転中の安全配慮)

- 通知は音声読み上げ対応必須(画面注視は危険・違反リスク)
- 優先度 3 段階:緊急(運転見合わせ発生)/ 予告(イベント終演 30 分前)/ 情報(今夜の雨予報)
- 通知頻度上限を設定(1時間に最大 3 件など)。うるさいアプリは即アンインストールされる

## 5. データベース設計(主要テーブル)

```sql
-- 会場マスタ

```

## 8. リスクと留意点

1. **地理営業区域の規制** — タクシーは営業区域(東京特別区・武三地区など)が法定されている。区域外への誘導提案をしない設計が必要
2. **スクレイピングの規約** — イベント・運行情報の取得元サイトの利用規約を個別確認。API 提供元を優先する
3. **運転中操作の安全性** — ながら運転(道路交通法違反)を助長しない UI。音声中心・停車中操作前提の設計を明記
4. **位置情報プライバシー** — 運転手の位置履歴は需要予測の資産になるが、取得目的の明示と同意取得が必須
5. **競合** — GO などの配車アプリは需要予測機能(お客様探索ナビ等)を内包しつつある。「流し・個人タクシー特化」「配車アプリに乗らない需要(イベント直後の路上需要)に強い」という差別化を明確に
